# 穿搭 Tab 单句输入 Skill 横向实验设计

## 目标

以完全相同的一句自然语言，验证飞书市场调研表中 10 个原型 Skill 的直接生成能力，并把每项真实结果以“代表截图 + 可点击 Demo 链接”回填至“生成demo：穿搭tab”列。

固定输入仅为：

> 请帮我设计一个抖音商城独立端app中的穿搭tab的高保真可交互原型。

## 实验对象

1. `prd-to-editable-demo v0.2.0`
2. `figma-flow-to-html-demo`
3. `Traemi：业务诉求到 Demo`
4. `ecommerce-design-language`
5. `inspire-prototype`
6. `prototype-builder`
7. `prd-generator`
8. `pm-kakaxi-skills`
9. `Aime 原型生成 Skill`
10. `huashu-design`

## 公平性规则

- 每个 Skill 在独立目录和独立运行记录中执行，只接收固定输入句，不补充 PRD、截图、Figma、品牌素材或口头解释。
- 严格遵循各 Skill 自身的入口判断、提问、生成和验证流程，不用另一个 Skill 替代失败项。
- Skill 如果要求补充材料、无法启动、无访问权限或无法生成 Demo，保留真实状态并标记为“未生成 Demo”。
- 不人工修复、美化或补全生成结果；只允许为已有本地 HTML 做不改变内容的静态托管。
- Skill 原生提供托管链接时保留原生链接；仅有本地 HTML 时统一托管，形成可访问链接。

## 产物与证据

每个实验单元保留：

- 原始运行记录和终态；
- 原生生成物或平台资产；
- 至少一张能代表最终效果的截图；
- 可点击 Demo 链接，或无法生成时的状态截图与原因；
- 基础浏览器验证结果，包括页面可打开、主要控件可点击和阻断错误。

飞书表格中的成功项使用“代表截图 + 查看可交互 Demo”结构；失败项使用“状态截图 + 未生成 Demo：原因”，不伪造链接。

## 执行与托管策略

采用“原生优先、统一兜底”：

1. 使用 Skill 原生平台或托管能力生成时，直接记录其原生 URL。
2. Skill 只产出本地 HTML 时，保持文件不变并发布到统一静态托管入口。
3. Skill 只产出文档、分析或制作清单时，如实记录该产物，不二次转成 Demo。
4. 需要额外输入才能继续时停止该实验，不替用户补充输入。

## 验证口径

成功 Demo 至少验证：

- 链接可访问且首屏正常显示；
- 至少一个核心交互产生可见反馈；
- 页面未出现阻断性脚本错误；
- 截图来自该 Skill 的实际结果，而非统一重制页面。

实验看板并排展示 10 项状态、截图和入口，便于比较自然语言直出能力、视觉完成度、交互完整度与交付形态。看板仅聚合证据，不修改任何 Skill 的产物。

## 飞书回填

- 只更新现有表格“生成demo：穿搭tab”一列，不改动 Skill 名称、定义、来源和安装包。
- 每完成并验证一个实验即保存证据；待 10 项均达到明确终态后统一回填，避免半成品混入市场调研结论。
- 回填后重新读取整张表，核对截图、链接、失败说明及原有附件均保留。

## 完成标准

- 10 个实验都有明确终态：成功、需要补充输入、不适用或阻断。
- 每个成功项都有真实截图、可点击链接和基础交互验证。
- 每个失败项都有可核查状态截图和一句话原因。
- 飞书表格目标列全部填充，并完成回读验证。
- 可视化对比页能打开全部成功 Demo，并清楚呈现失败项。
