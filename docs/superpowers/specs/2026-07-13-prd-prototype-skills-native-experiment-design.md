# PRD → 可交互原型 Skills 原生能力实验设计

## 1. 实验目标

以两份飞书文档作为固定输入，验证当前环境中六个主力原型能力在真实原生流程下的实际运行效果，并回答三个问题：

1. 每个能力能否直接消费对应文档并生成可运行、可点击的原型？
2. 各能力在需求忠实度、交互、视觉、稳定性和交付形态上分别表现如何？
3. 面对“大型产品迭代方案”和“单功能 PRD”两类不同输入，哪个能力更合适、表现更稳定？

## 2. 固定输入

### 输入 A：穿搭 Tab 迭代方案

- 来源：`https://bytedance.larkoffice.com/wiki/HxxGwwkxAiLf9BkiSWgcWXcanbA`
- 特征：市场调研、竞品分析、方向判断、四模块产品方案、分期指标和大量参考图。
- 预期原型范围：二级分类、理由型 Feed 卡片、详情页解释、商品/平替、AI 搭配与 AI 试穿承接。

### 输入 B：AI 试穿新增拍照输入

- 来源：`https://bytedance.larkoffice.com/docx/G2S7dXD5Boj5FSxOQYJcuCxJnDd`
- 特征：问题和指标清楚，范围集中，包含创建形象、拍照、拍摄确认、审核结果和重新上传链路。
- 预期原型范围：创建形象浮层、拍照页、摄像头翻转/相册/关闭、重拍/使用照片、审核成功与失败。

实验开始时将两份文档固化为安全、等价、可复现的 fixture。真实抓取返回的原始正文不直接进入 Git，而是先计算 `originalContentSha256`；正文中所有带临时授权 query 的图片都下载到对应输入的本地 `assets/`，按实际 MIME 类型选择扩展名并计算 SHA-256。`source.md` 仅把这些图片 URL 替换为相对本地路径，其他文字与结构不得改写，并计算 `fixtureSha256`。`metadata.json` 记录来源文档、revision、抓取时间、`originalContentSha256`、`fixtureSha256`、`transformation` 和 `assetCount`；`assets-manifest.json` 只记录本地文件、MIME、字节数、SHA-256、`sourceReferenceIndex` 和 `sourceAltTextSha256`，禁止保存原始授权 URL。所有 tracked 文件必须通过扫描，不能包含 `authcode` 或 `code` query。所有实验单元只读取对应安全 fixture 及自身 Skill 允许读取的通用资源。

## 3. 实验对象

### 六个主力能力

1. Open Design
2. 花叔 Design（`huashu-design`）
3. `prd-generator`
4. `pm-kakaxi-skills`
5. `vne-prototype`
6. `inspire-prototype`

### 输入适配性检查

- `figma-flow-to-html-demo`：检查两份输入是否满足“多张静态流程图 + 对应切图”的硬前提；不满足时记录为“不适用”，不强行生成。
- `sites:sites-building`：记录其可消费需求生成网站，但属于通用建站而非专门 PRD 原型流程；本轮不纳入六强排名。

## 4. 实验结构与隔离

建立 `2 × 6 = 12` 个独立实验单元。每个单元包含：

- `input/`：唯一输入文档副本、来源与哈希。
- `run/`：原生流程日志、问题与回答、依赖和异常。
- `artifact/`：Skill 原生交付物，不统一改造成相同技术栈。
- `qa/`：自动检查、浏览器截图、交互路径和错误记录。
- `result.json`：评分、偏离项、状态和产物入口。

隔离规则：

- 不允许读取其他实验单元的代码、截图、页面清单、设计说明或评分。
- 同一 Skill 处理第二份输入时也使用新目录和干净上下文。
- 可以读取自身 Skill 说明要求的模板、脚本、设计系统和平台资源。
- 不人为统一技术栈、页面数量、视觉风格或交付格式；这些差异本身属于原生能力结果。
- 若 Skill 原生要求提问，优先从输入原文中回答。只有原文无法判断且答案会改变核心产品范围或设计方向时，才向用户请求决定。

## 5. 原生能力执行原则

- 完整遵循每个 Skill 的入口判断、设计流程、输入门槛、验证流程和交付规范。
- 不以统一盲测指令覆盖 Skill 自带的提问、设计方向探索或质量门禁。
- Skill 要求的平台登录、MCP、CLI、依赖安装或网络访问应真实执行；失败时记录错误，不伪造成功。
- 原始文档内图片应按固定输入规则下载到本地 `assets/` 并由 `assets-manifest.json` 校验；图片鉴权过期或无法下载时记录素材降级，不用虚构图片冒充，也不得把临时授权 URL 写入任何 tracked 文件。
- 平台型能力保留平台 Asset、预览链接和生成日志；本地型能力保留源文件、构建产物和启动方法。
- 原生流程无法继续时，状态记为 `BLOCKED` 或 `NOT_APPLICABLE`，并保留已完成步骤；不得用另一个 Skill 代做。

## 6. QA 与评分

### 统一评分（100 分）

| 维度 | 分值 | 核心判据 |
|---|---:|---|
| 需求忠实度 | 20 | 页面、规则、文案和状态能追溯到输入；无关键误读或无依据扩写 |
| 核心流程覆盖 | 15 | 文档要求的主任务能端到端走通；关键页面和分支无缺失 |
| 交互真实性 | 20 | 可见控件可操作；跳转、表单、状态变化、异步反馈不是死按钮 |
| 视觉与信息层级 | 15 | 与产品语境匹配；移动端信息清晰；重点、层级和操作优先级合理 |
| 异常与边界状态 | 10 | 空态、加载、失败、关闭/返回、重试、删除等适用状态得到处理 |
| 运行稳定性 | 10 | 可启动、无阻断脚本错误、关键路径无页面错误、刷新后行为合理 |
| 交付与迭代能力 | 10 | 产物可访问、启动说明明确、结构可维护，并支持后续修改或交接 |

### 验证方法

1. 静态检查：文件存在、构建成功、资源引用、脚本语法和明显死链。
2. 浏览器检查：统一桌面浏览器窗口，移动端原型使用统一移动 viewport；记录 `pageerror` 和控制台错误。
3. 关键路径点击：输入 A、B 分别使用固定任务脚本；每个原型至少完整执行一次主路径。
4. 状态检查：触发所有与文档相关的浮层、加载、成功、失败、重试和删除状态。
5. 视觉证据：每个实验至少保存入口、关键中间态、结果/失败态三类截图；多屏交付按实际屏数补充。
6. 原生偏离检查：逐条列出因环境、权限或输入不足导致的流程偏离，并在相关评分维度扣分。

评分以实际可操作产物为准，不因 Skill 文档宣称某项能力而给分。无法运行的环节不按“推测可用”评分。

## 7. 排名与结论

- 输入 A 与输入 B 分别排名，不合并成一个总榜。
- 为每个 Skill 计算跨输入差值，评价稳定性和适用边界。
- `BLOCKED` 单元仍进入报告，但不与成功产物用虚构分数竞争；报告明确阻断原因。
- 除数字评分外，每个 Skill 给出：最佳表现、主要缺陷、最适用场景、不建议使用的场景。
- 最终给出任务路由建议，而不是宣称存在适合所有 PRD 的单一赢家。

## 8. 视觉看板

浏览器看板包含：

1. 实验概览：12 个单元状态、耗时、产物类型和阻断信息。
2. 输入 A 排名：得分雷达/分项条形、关键截图和可点击原型入口。
3. 输入 B 排名：同上。
4. Skill 详情：原生流程轨迹、问题与回答、截图、QA、评分依据和偏离项。
5. 跨输入对比：同一 Skill 在两种 PRD 上的稳定性及能力边界。
6. 适配性检查：`figma-flow-to-html-demo` 与 `sites:sites-building` 的纳入/排除依据。

看板只引用真实产物和验证数据，不替各 Skill 修复或美化原型。

## 9. 失败与恢复

- 网络、认证或权限失败：保留原始错误和所需恢复动作，修复后从该实验单元继续。
- 依赖安装失败：先尝试 Skill 官方降级路径；无降级路径则标记阻断。
- 构建失败：保留源码和构建日志，不私自切换技术栈重做。
- 原型生成超时：按 Skill 官方查询/续跑方式恢复；不重复发起造成多个不可区分 Asset。
- 文档在实验期间更新：继续使用已固化 revision，避免不同 Skill 获得不同输入；新版另开实验批次。

## 10. 完成标准

实验完成需同时满足：

- 12 个主实验单元均有明确终态：`PASS`、`PASS_WITH_CONCERNS`、`BLOCKED` 或 `NOT_APPLICABLE`。
- 所有成功原型完成真实浏览器关键路径验证。
- 两份输入分别完成评分和排名。
- 视觉看板可打开，能访问本地产物或平台预览链接。
- 最终报告包含证据、偏离项、适用边界和推荐路由。
