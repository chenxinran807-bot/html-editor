# PRD 忠实执行与视觉参考契约设计

## 背景

`prd-to-editable-demo` 已能读取 PRD、形成语义需求并生成原型，但仍存在两类关键失败：

1. PRD 不清晰时，模型自行补全会改变页面结构、内容或用户动线；
2. PRD 已清晰时，模型仍可能遗漏、改写或用通用设计模式替代已明确要求。

当用户提供多张图片时，模型还容易把图片混合成模糊情绪板，无法准确执行“图 A 参考颜色、图 B 还原结构、图 C 参考组件”等局部指令。

## 目标

Skill 的唯一最高目标是**可见产品忠实度**：最终原型准确呈现 PRD、用户确认结果和指定视觉参考所描述的页面结构、相对位置、内容文案、视觉表达、核心动线与轻量交互反馈。

一句话定位：

> 将 PRD 和指定视觉参考无损转换为经用户确认的执行基线，并生成可逐项证明其忠实度的交互原型。

## 第一性原理

Skill 只需可靠完成四件事：

1. 不丢失地理解；
2. 让用户消除影响结果的不确定性；
3. 严格执行确认后的要求；
4. 用可见结果证明执行正确。

生成工具、Inspire 路由和工程交付属于执行层，不得凌驾于上述目标。

## 设计原则

### 可见产品忠实度优先

页面结构、相对位置、内容文案、核心视觉表达、默认状态和轻量交互反馈，与核心页面和主流程同级。权限、异常和边界逻辑仅在 PRD 明确要求或影响当前评审体验时提升优先级。

### 结构化不得降级信息

结构化需求不是摘要，而是无损、显式、可执行的中间表示。PRD 中的正文、表格、图片标注、备注和验收要求必须全部建立映射。复杂需求应拆成原子要求，但不得丢失条件、例外、数值、强约束或原文证据。

### 信息保留不等于进入界面

无损理解必须保留 PRD 全部信息，但只有产品需求可以进入页面和交互。市场调研、业务指标、竞品分析、方案论证、优先级标签和项目背景属于决策上下文；除非 PRD 明确要求面向用户展示，否则不得转成页面文案或组件。

### 不确定性不得静默裁决

任何会影响核心页面、页面呈现、用户动线或关键交互的缺口与冲突，必须由用户确认。模型不得根据行业惯例、实现难度或推测的新旧版本自行选择。

### 内部完整，外部简洁

系统内部一次完成全量分析；面对用户时采用渐进确认。每轮只处理一个主题、最多呈现 1–3 个高影响决策。默认只展示结论、影响和推荐选项，完整原文证据与分析保存在可展开的确认包中。

## 四份核心契约

### 1. 理解契约

输入是 PRD、补充文字、表格、截图和参考图片；输出是无损需求 IR。

IR 至少包含：

- 用户角色、目标与场景；
- 业务对象、字段、状态及关系；
- 页面、弹窗、区域和界面状态；
- 页面目的、内容、文案和默认状态；
- 模块层级、顺序、相对位置、固定或滚动行为；
- 用户动作、触发元素、前置条件和可见反馈；
- 页面之间的跳转、切换、展开、返回和状态恢复关系；
- 视觉要求、素材要求和禁止项；
- 原文证据、来源位置和确定性。

每个信息单元还必须标记用途：

- `product_requirement`：决定用户可见页面、内容、交互或状态；
- `acceptance_criterion`：用于验收，但不直接进入界面；
- `design_constraint`：约束生成方式或视觉结果；
- `business_context`：帮助理解目标，但不进入产品；
- `research_evidence`：市场、竞品或用户研究资料；
- `delivery_metadata`：优先级、排期、负责人或发布说明。

只有 `product_requirement` 可以默认生成用户界面。其他类型若要进入界面，必须有独立、明确的产品需求证据。

确定性类型为：`explicit`、`derived`、`confirmed`、`assumed`、`missing`、`conflicting`。`derived` 只能表达由原文必然得到的关系，不得新增业务事实。

进入确认阶段前必须满足：所有有效 PRD 信息均被映射，未映射信息为零。

### 2. 确认契约

确认对象仅限会影响最终页面或核心体验的缺口、冲突和高影响推断。已明确且无冲突的内容不要求用户逐条复核。

交互规则：

- 每轮一个主题；
- 每轮最多 1–3 个相互关联的决策；
- 先给推荐方案，再给简短理由和其他选项；
- 明确说明该问题影响哪些页面或动线；
- 原文证据默认折叠；
- 用户可回答选项，也可直接修正文案或描述；
- 当前轮确认后再进入下一轮，不展示长篇总报告。

存在多个问题时，系统内部按页面和影响排序形成队列：页面样子与核心体验优先，影响演示的异常与权限其次，不影响当前评审的工程细节不阻断。

用户确认结果必须记录原答案、时间、关联需求和替代的阻断项。所有阻断项解决前不得生成原型。

### 3. 执行契约

确认完成后生成版本化 `requirements-baseline`。生成模型只执行该基线，不得重新自由解释 PRD。

优先级为：

1. 用户最新明确确认；
2. PRD 明确要求；
3. 用户确认的图片参考绑定；
4. 已确认的必然推导；
5. 通用产品设计规范；
6. 模型设计建议。

每个页面形成独立执行切片，包含页面目标、必需区域、模块顺序、明确文案、关联动作、页面关系、视觉参考和验收标准。逐页生成、逐页检查，通过后再生成下一页。

页面和组件不得作为互相独立的清单生成。执行切片必须同时属于一条端到端用户路径，并建立以下映射：

```text
PRD 模块 → 页面位置 → 组件 → 界面状态 → 触发动作 → 下一页面或状态
```

对于具有层级的信息架构，IR 必须保留父子、包含、互斥和筛选关系，不得把不同层级的分类扁平化为并列入口。

每个核心任务必须定义最小闭环：入口、选择或操作、内容承载、详情或结果、下一步承接以及返回路径。缺少任一必要节点时，该任务不得标记为已实现。非核心功能的丰富度不能抵消核心闭环缺失。

用户修改要求时创建新基线版本，并记录受影响的页面、元素和交互；不得覆盖历史确认，也不得让未受影响页面发生无关漂移。

### 4. 验收契约

生成后从结果反向验证基线：

- 页面和状态是否齐全；
- 模块、顺序和相对位置是否正确；
- 明确文案是否准确；
- 核心视觉重点是否符合 PRD；
- 页面关系、触发动作和可见反馈是否正确；
- 图片指定参考项是否执行；
- 禁止借用的图片属性是否未被使用；
- 是否存在未经确认的重要新增设计。

验收必须区分三种存在状态：

- `declared`：只存在于 PRD、文案或代码声明中；
- `rendered`：已在页面上可见；
- `reachable-and-functional`：用户可从规定入口到达，并产生规定的状态变化或页面结果。

只有 `reachable-and-functional` 才能计为交互能力完成。弹出占位提示、不可达页面或静态文案不得冒充功能闭环。

发现明确执行错误时自动修正并重新验证；发现新的产品歧义时暂停，仅向用户提出当前最高影响的一组问题。

## 多图片视觉参考协议

每张参考图建立独立绑定，不得默认混合成整体情绪板。绑定内容包括：

- 作用范围：全局、页面、区域或元素；
- 参考维度：结构、相对位置、比例、间距、颜色、字体、图标、素材、裁切、组件、文案风格或交互反馈；
- 还原强度：精确还原、高度参考、局部借鉴、仅取灵感；
- 禁止使用：明确排除不应借用的属性；
- 图片区域：必要时标记具体区域及其用途。

模型分析图片后，只向用户展示简洁理解，例如：“图 B 用于目标页面；精确还原首屏结构；高度参考卡片比例；不参考颜色和品牌。”用户确认后写入执行基线。

当图片与 PRD 或不同图片之间存在影响页面结果的冲突时，模型必须说明冲突及影响，并让用户选择；不得自动融合。

## 数据产物

核心产物包括：

- `prd-source-map.json`：PRD 原始信息单元及来源；
- `requirements-ir.json`：无损需求结构；
- `page-flow-graph.json`：页面、状态、触发和流转；
- `visual-reference-manifest.json`：逐图参考绑定；
- `clarification-queue.json`：内部问题队列；
- `confirmation-record.json`：用户确认记录；
- `requirements-baseline.json`：冻结执行基线；
- `traceability-matrix.json`：需求、图片与原型元素映射；
- `fidelity-report.md`：偏差、修正与最终验收结果。

这些文件主要供系统执行和追溯，不应默认全部展示给产品经理。

## 交付门槛

可客观验证的项目必须满足：

- PRD 有效信息映射率为 100%；
- 明确文案准确率为 100%；
- 核心页面和已确认动线覆盖率为 100%；
- P0 可见需求覆盖率为 100%；
- 精确还原参考项全部通过；
- 未解决阻断项为零；
- 未解释的重要新增设计为零。

验收必须针对用户实际要求的最终交付物。本地 HTML 直接验证最终文件或本地服务中的核心路径，不要求额外发布。只有用户明确要求在线链接，或最终容器本身是在线平台时，才增加线上验收；此时必须从最终链接按核心用户路径逐步点击，验证页面加载、资源、跳转、状态变化和返回行为。

“高级感”“原生感”或“整体风格相似”等主观目标不能伪装成百分比，必须拆成可观察属性并辅以主观视觉验收。

视觉质量是独立维度，不能抵消产品结构、信息架构、可达性或动线错误。高保真但核心闭环失败的原型仍判定为失败。

## 测试策略

除文档和结构测试外，必须加入行为测试：

- PRD 清晰时不追问已明确内容；
- 背景资料、调研结论、业务指标和优先级标签不得自动进入用户界面；
- 核心布局缺失时暂停生成；
- PRD 冲突时不得自行裁决；
- 明确文案不得改写；
- 两层或多层信息架构不得被扁平化；
- 图片仅参考颜色时不得复制结构；
- 图片要求还原结构时必须保留结构关系；
- 多张图片的作用范围不得混淆；
- 用户确认后不得恢复旧理解；
- 用户修改一页时不得造成其他页面无关漂移；
- 声明存在但不可达或无状态变化的功能不得通过验收；
- 核心路径必须从入口到结果再到返回完整走通；
- 用户要求在线交付时，本地通过但最终链接失败不得判定完成；
- 每轮确认不得超过一个主题和三个高影响决策。

测试应检查真实产物和决策轨迹，不能只检查 `SKILL.md` 是否出现关键词。

## Skill 结构

用户仍然只调用一个 `prd-to-editable-demo` 工作流 Skill。内部按需读取五个聚焦协议：

```text
prd-to-editable-demo
├── requirements-understanding
├── clarification
├── execution-contract
├── visual-reference
└── fidelity-verification
```

这不是五个独立安装入口。主 Skill 负责阶段编排，协议文件负责各自单一职责。Inspire、HTML 或其他生成容器在执行契约之后选择，不改变需求基线。

## 非目标

- 不把 Skill 扩展成通用需求管理平台；
- 不要求产品经理审核完整 IR；
- 不为不影响评审的工程边界阻塞生成；
- 不声称可对任意参考图实现未定义的“100% 视觉一致”；
- 不用长篇分析代替明确推荐和短确认；
- 不让生成工具的能力边界悄悄改变产品要求。
